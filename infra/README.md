# Окружение VPS: notenotes и остальные приложения

Ansible-конфигурация для Netcup VPS Lite 1 G12s (Ubuntu 24.04, 2 vCore / 4 GB RAM / 80 GB SSD).
Доводит чистый сервер до состояния, с которого можно начинать Фазу 1 из [ТЗ](TZ.md) §19.

Схема рассчитана на **несколько приложений на одной машине** — так, чтобы новое
приложение добавлялось отдельной ролью, не задевая уже работающие.

## Схема хоста

```
/srv/edge/          Общий reverse proxy (Caddy). НЕ зависит от шифрованного тома,
                    поднимается при загрузке сам.
  caddy/            монтируется в контейнер ЦЕЛИКОМ, не отдельными файлами
    Caddyfile       import conf.d/*.caddy
    conf.d/
      00-default.caddy   только комментарии, держит глоб непустым
      notenotes.caddy    ← кладёт роль notenotes_stack
  data/, config/    сертификаты и состояние Caddy

/srv/encrypted/     ОДИН LUKS-том на приложения, которым нужно шифрование.
  notenotes/        postgres/, redis/, uploads/, secrets/, backup-staging/
  swapfile

/srv/notenotes/     compose-проект приложения (без секретов)
  compose/docker-compose.yml, initdb/

/srv/politrain/     Приложение БЕЗ шифрования: данные лежат прямо здесь,
                    поэтому оно поднимается при загрузке само, без unlock.
```

Приложения делятся на две категории, и от этого зависит только одно — нужен ли
им ручной unlock после перезагрузки:

| | Данные | Юнит | После ребута |
|---|---|---|---|
| **notenotes** | `/srv/encrypted/notenotes/` | `WantedBy=encrypted-apps.target` | ждёт `make unlock` |
| **politrain** | `/srv/politrain/data/` | `WantedBy=multi-user.target` | поднимается сам |

politrain — самоучитель польского без персональных данных, шифрование ему не
нужно, поэтому он в незашифрованном каталоге. Практический выигрыш: после ребута
он работает сразу, а не ждёт, пока ты введёшь пароль от чужого тома.

Ключевые развязки, и зачем они:

- **Прокси вне шифрованного тома.** Иначе одно приложение, ждущее ввода
  парольной фразы, держало бы недоступными все остальные. Упал notenotes —
  Caddy жив и отдаёт 502 только по его имени, соседи работают.
- **Один том на все приложения, а не по одному.** Один пароль и одна команда
  после перезагрузки вместо N. Разделение — подкаталогами.
- **Caddyfile из фрагментов.** Каждое приложение владеет только своим файлом
  в `conf.d/`; добавление приложения не требует правок чужих конфигов.
- **Каталог конфигурации монтируется целиком.** Bind-mount отдельного файла
  привязан к inode, а Ansible пишет шаблоны атомарно (temp + rename) — inode
  меняется, и контейнер навсегда остаётся со старой версией. Ошибки при этом
  нет: reload проходит успешно и применяет устаревший конфиг.
- **Сети:** общая `edge` (только Caddy и «фронтальные» контейнеры) плюс
  приватная `<app>_internal` на приложение. Postgres notenotes не виден
  из контейнеров других приложений.
- **Приложения запускаются через `encrypted-apps.target`.** Каждый сервис
  объявляет `WantedBy=encrypted-apps.target`, поэтому `encrypted-unlock`
  не нужно править при добавлении приложения.

### Добавление второго приложения

Общее для любого приложения:

1. Роли `<app>_layout` и `<app>_stack` по образцу `notenotes_layout` / `notenotes_stack`.
2. Свой фрагмент `/srv/edge/caddy/conf.d/<app>.caddy` — только он определяет,
   по какому домену приложение доступно.
3. Приложение **не публикует портов на хост**. Единственный владелец 80 и 443 —
   Caddy; наружу приложение попадает через сеть `edge`. Поэтому конфликтов
   портов между приложениями не бывает в принципе.
4. Приватная сеть `<app>_internal` для его БД плюс подключение к `edge`.
   В `edge` — **обязательно явный alias** вида `<app>-backend`: сеть общая,
   и два сервиса с именем `backend` столкнулись бы по DNS, после чего Caddy
   начал бы попадать в чужой контейнер.
5. A-запись `<app>` → `188.68.40.209` в панели Hostens.

Дальше зависит от того, нужно ли приложению шифрование.

**Нужно** (как notenotes): каталог в `/srv/encrypted/<app>/`, юнит с
`RequiresMountsFor=/srv/encrypted`, `ExecStartPre=/usr/local/sbin/encrypted-preflight <app>`
и `WantedBy=encrypted-apps.target`. В compose — `restart: on-failure`,
иначе Docker поднимет контейнеры при загрузке, до разблокировки тома.

**Не нужно** (как politrain): каталог `/srv/politrain/data/`, юнит с обычным
`WantedBy=multi-user.target`, без `RequiresMountsFor` и без preflight.
В compose можно `restart: unless-stopped` — ловушки с пустым каталогом поверх
точки монтирования здесь нет, монтировать нечего.

**Про память — это главное ограничение, а не архитектура.** Текущий стек:
Caddy 128 МБ + Postgres 2 ГБ + Redis 384 МБ ≈ 2.5 ГБ из 4, и это ещё без
backend'а и воркера notenotes (~1.2 ГБ). Второе приложение с собственным
Postgres сюда не влезет. Если ему понадобится база — заводить отдельную БД
и роль в **существующем** экземпляре Postgres, а не второй контейнер: два
инстанса по 256 МБ `shared_buffers` работают хуже одного на 1 ГБ.

## Модель безопасности — прочитать до запуска

Шифрование многослойное, и слои закрывают **разные** угрозы. Путать их нельзя.

| Угроза | Что защищает |
|---|---|
| Утёк бэкап или снапшот | шифрование restic |
| Хостер списал диск, украден образ выключенной VM | LUKS-том (ключ не на диске — фраза вводится вручную) |
| Взломали живой сервер, получили root | **ничего из перечисленного** — ключ уже в памяти |
| Хостер читает RAM через гипервизор | **ничего из перечисленного** |

Последние две строки закрываются только client-side шифрованием — «сейф» из
ТЗ §16.2, где пароль не покидает браузер. Он реализуется в приложении (Фаза 4).

> **До реализации сейфа PII в общее хранилище не кладём.** Паспорта, финансовые
> документы и подобное ждут §16.2. Это не перестраховка: по ТЗ §16.1 бэкенду
> нужен плейнтекст для LLM, OCR и векторного поиска, поэтому в общем хранилище
> данные принципиально доступны рантайму.

Три вещи, без которых LUKS-том обесценился бы, и они учтены:

1. **Секреты внутри тома.** `.env`, пароль restic и ключи S4 лежат в
   `/srv/encrypted/notenotes/secrets/`. Иначе образ незашифрованного диска
   отдавал бы доступ к расшифровке всех бэкапов.
2. **Своп не на открытом диске.** Единственный swapfile лежит внутри
   шифрованного тома. Обычный swapfile на root хранил бы расшифрованные
   страницы Postgres открытым текстом.
3. **Короткая ретенция journald** (14 дней). Логи лежат на незашифрованном root
   и неизбежно копят метаданные.

Одно осознанное исключение: **приватные ключи TLS лежат на открытом диске**
(`/srv/edge/data`). Сертификаты ротируемы — отозвал и перевыпустил, — в отличие
от пользовательских данных. Держать их в томе означало бы «нет HTTPS до unlock».

## DNS

Зона `metallcorn.online` обслуживается `ns1/ns2.hostens.com`. Две особенности,
которые уже есть в зоне и влияют на переезд:

**Есть wildcard `*` A → `155.212.217.213`.** Поэтому любой поддомен, включая
`notenotes`, уже резолвится — но на старый хост. Явная A-запись перебивает
wildcard (более точное совпадение), поэтому для запуска wildcard трогать не надо.
Неизвестные имена получают 404 от самого Caddy — отдельный catch-all для этого
не нужен и был бы вреден, см. раздел «Неочевидные места».

**`politrain.metallcorn.online` существует как AAAA → `2a01:4f9:4a:1a51::235`**
(Hetzner), A-записи у него нет. Имя есть в зоне, поэтому wildcard на него
не действует (RFC 4592).

### Записи для notenotes

| Поле | Значение |
|---|---|
| Type | `A` |
| Name / Host | `notenotes` |
| Value | `188.68.40.209` |
| TTL | `3600` |

Запись создана и работает: `notenotes.metallcorn.online` → `188.68.40.209`.

Проверка перед включением TLS:

```bash
dig +short A notenotes.metallcorn.online @ns1.hostens.com   # ждём 188.68.40.209
dig +short A notenotes.metallcorn.online                     # должно совпасть
```

Второй запрос какое-то время отдаёт старый IP из кэша (текущий TTL 14400 = 4 ч).
Let's Encrypt ходит к авторитативному NS, но дождаться совпадения обоих дешевле,
чем разбирать неудачную валидацию.

### При переносе politrain

**Недостаточно добавить A — надо удалить AAAA.** Если оставить AAAA на Hetzner,
клиенты в IPv6-сетях (почти все мобильные) пойдут по IPv6 на старый хост. Если он
ещё жив, получится расщепление: часть пользователей видит новое приложение, часть
старое, и в логах нового сервера этого не видно вообще.

IPv6 на этой машине пока не настроен: `docker_ipv6_enabled: false`. Включать
**вместе** с созданием AAAA, не раньше — AAAA без IPv6 в Docker означает, что
v6-клиенты не смогут подключиться. Перед этим проверить `ip -6 addr` на сервере.
Скрипт `docker-user-firewall` правила `ip6tables` уже умеет.

## Шаг 0 — локальная подготовка (один раз)

```bash
pipx install --include-deps ansible
make deps

ssh-keygen -t ed25519 -f ~/.ssh/notenotes_vps -C notenotes-vps
ssh-copy-id -i ~/.ssh/notenotes_vps.pub root@188.68.40.209   # спросит root-пароль Netcup
```

`ssh-copy-id`, а не Ansible с `-k`: не нужен `sshpass`, и root-пароль не проходит
через Ansible. Дальше всё идёт только по ключу.

Блок в `~/.ssh/config`:

```
Host notenotes
    HostName 188.68.40.209
    User metallcorn
    IdentityFile ~/.ssh/notenotes_vps
    IdentitiesOnly yes
```

Секреты (список — в `inventory/group_vars/all/vault.example.yml`):

```bash
ansible-vault create inventory/group_vars/all/vault.yml
```

Генерировать значения: `openssl rand -base64 32`.

> **Сохрани отдельно в менеджере паролей:** `vault_luks_passphrase` и
> `vault_restic_password`. Без первой не открыть каталог данных, без второй не
> расшифровать бэкапы. Потеря любой из них — безвозвратная потеря данных.

Для бэкапов нужен бакет в панели MEGA S4 и пара ключей доступа. S4 включён во все
планы MEGA Pro. Если ключей пока нет — поставь `restic_backend: local`
в `inventory/group_vars/all/main.yml`, потом переключишь на `s4`.

## Шаг 1 — прогон

```bash
make bootstrap   # юзер metallcorn + ключ + sudo (под root, один раз)
make harden      # sshd, ufw, fail2ban, обновления безопасности
make platform    # docker + шифрованный том + edge-прокси
make stack       # приложение notenotes: postgres+pgvector, redis, фрагмент Caddy
make backup      # restic + таймеры
```

Либо `make site` для шагов 2–5 одним прогоном. `make check` прогоняет всё
в `--check --diff`, ничего не меняя.

`make harden` отключает вход root и парольную аутентификацию. Роль сама
проверяет доступ до и после, но **проверь вход вторым терминалом, не закрывая
текущую сессию** — разбираться через VNC-консоль Netcup дороже.

## Повседневные операции

### После каждой перезагрузки

Сами поднимаются: edge-прокси и приложения без шифрования (politrain).
Ждёт ручного действия только notenotes — его данные зашифрованы. Пока он не
разблокирован, Caddy отдаёт по его имени 502, то есть «сайт лежит», а не
«сервер недоступен», и на соседей это не влияет.

```bash
make unlock        # или: ssh notenotes 'sudo encrypted-unlock'
```

Скрипт спросит парольную фразу, смонтирует том, подключит своп и поднимет
**все** приложения через `encrypted-apps.target`.

Обратная операция — `sudo encrypted-lock`: останавливает приложения, отмонтирует
и закрывает том. Нужна перед плановым ребутом и для проверки, что приложения
действительно не стартуют без разблокировки. Прокси при этом не трогается.

Авто-ребут в unattended-upgrades **выключен** именно поэтому: иначе сервер
поднялся бы без тома и приложения лежали бы до ручного unlock. Обновления
безопасности ставятся автоматически, ядро перезагружается вручную.

### Бэкапы

```bash
sudo notenotes-backup-now                 # обязательно перед миграцией БД (ТЗ §17)
sudo notenotes-restore-test               # сквозная проверка восстановления
sudo notenotes-restic snapshots           # список снимков
sudo notenotes-restic check               # целостность репозитория
systemctl list-timers 'notenotes-*'       # расписание
journalctl -t notenotes-alert --since -7d # были ли отказы
```

Бэкапится дамп Postgres (`pg_dump -Fc`), каталог загрузок, секреты и compose-файл
приложения. Каталог `PGDATA` исключён намеренно: копия файлов живого кластера без
`pg_basebackup` непригодна для восстановления, а дамп консистентен по транзакции.
Конфиг edge-прокси не бэкапится — он целиком воссоздаётся из этого репозитория
командой `make platform`.

### Проверка восстановления

«Бэкапы делаются» и «из бэкапов можно восстановиться» — разные утверждения,
и второе проверяется только практикой:

```bash
sudo notenotes-restore-test
```

Скрипт достаёт последний снимок из MEGA S4, разворачивает дамп в отдельную
временную базу, проверяет расширения и векторный запрос, затем убирает за собой.
Рабочая база не затрагивается. Прогонять после изменений в схеме бэкапов
и хотя бы изредка планово.

### Доступ к БД с ноутбука

Postgres и Redis слушают только `127.0.0.1` — Docker публикует порты в обход UFW,
поэтому `0.0.0.0` означал бы базу, открытую в интернет. Штатный путь:

```bash
ssh -L 5432:localhost:5432 notenotes
psql -h localhost -U notenotes -d notenotes
```

TCP-форвардинг в sshd оставлен включённым именно ради этого.

## TLS

Включён: `notenotes_tls_mode: acme`. Caddy получил сертификат Let's Encrypt
по HTTP-01 и продлевает его сам. HTTP отвечает редиректом 308 на HTTPS.

Переключатель общий для всех сайтов хоста. При добавлении приложения менять
ничего не нужно — достаточно A-записи и фрагмента в `conf.d/`.

## Неочевидные места

Четыре ловушки, на которые потрачены отдельные предохранители. Если менять
соответствующие роли — учитывать.

**1. Порядок файлов в `/etc/ssh/sshd_config.d/`.** sshd берёт **первое**
встреченное значение каждого ключа, а `Include` стоит в начале `sshd_config`
и читает каталог в лексикографическом порядке. cloud-init кладёт туда
`50-cloud-init.conf` с `PasswordAuthentication yes`. Поэтому наш drop-in
называется `01-notenotes-hardening.conf` — с префиксом `99-` он бы проиграл,
и хардненинг выглядел бы применённым, не будучи таковым. Роль проверяет
**эффективный** конфиг через `sshd -T`, а не содержимое файла.

Отдельно: Ubuntu 24.04 использует `ssh.socket`, а не `ssh.service`, поэтому
роль определяет режим — `reload ssh.service` при socket-активации упал бы
с «Unit is not active».

**2. Docker обходит UFW.** Docker вставляет правила в `FORWARD` и `nat`, минуя
цепочку `INPUT`, которой управляет UFW. Порт, опубликованный как
`0.0.0.0:5432`, остаётся доступен из интернета, хотя `ufw status` показывает его
закрытым. Закрыто двумя уровнями: публикация только на `127.0.0.1` и
default-deny в цепочке `DOCKER-USER` (`docker-user-firewall.service`).
Forward-политика UFW намеренно **не** управляется — Docker переставляет свои
хуки при каждом старте демона, и попытка ими управлять даёт гонку.

В правилах `DOCKER-USER` фильтрация идёт по порту **контейнера**, а не хоста:
DNAT происходит в `nat/PREROUTING`, то есть до `FORWARD`. Для Caddy маппинг
`80:80` и `443:443`, поэтому номера совпадают. Сервис с разными портами хоста
и контейнера потребует правки `docker_ingress_allowed_ports`.

**3. Docker сам создаёт каталоги bind-mount.** Если стек запустить при
незамонтированном томе, Postgres увидит пустой каталог и проинициализирует
**новый** кластер поверх точки монтирования. После unlock реальные данные
окажутся скрыты под томом, а приложение будет смотреть в пустую базу и выглядеть
работающим. Защита в три слоя: `restart: on-failure` вместо `unless-stopped`
(чтобы Docker не поднимал контейнеры при загрузке), `RequiresMountsFor=`
в юните приложения, и `encrypted-preflight`, проверяющий точку монтирования,
маркер-файл и каталог конкретного приложения.

**4. Bind-mount отдельного файла привязан к inode.** Ansible пишет шаблоны
атомарно: временный файл плюс `rename`. Inode меняется, и контейнер продолжает
читать старую версию файла — при этом `caddy reload` завершается успешно и
рапортует «config is unchanged», то есть отказ полностью бесшумный. Поэтому
каталог `/srv/edge/caddy` монтируется целиком. Каталоги этой проблемы не имеют,
поэтому фрагменты в `conf.d/` подхватывались, а сам Caddyfile — нет.

**5. Catch-all на порту 80 ломает выпуск сертификатов.** Первая версия
содержала блок `:80`, отдающий 404 на неизвестные имена. Он перехватывал в том
числе `/.well-known/acme-challenge/`, которым Let's Encrypt проверяет владение
доменом: валидация не проходила, сертификат не выпускался, Caddy слушал 443 без
возможности завершить рукопожатие. Отдельный catch-all не нужен — Caddy сам
отвечает 404, если ни один site-блок не совпал по Host.

**6. Хендлеры Ansible теряются при падении play.** Если прогон упал ПОСЛЕ записи
файла, но ДО хендлера, уведомление пропадает навсегда: на следующем прогоне файл
уже корректен, шаблон возвращает `ok`, хендлер не вызывается — и прокси остаётся
со старым конфигом, а Ansible рапортует успех. Поэтому роль `notenotes_stack`
сверяется с фактическим ответом прокси, а не с фактом изменения файла.

**7. `encrypted-apps.target` намеренно без секции `[Install]`.** Если бы цель
попадала в `multi-user.target`, systemd пытался бы поднять приложения при
загрузке — до разблокировки тома. Поэтому цель запускается только вручную из
`encrypted-unlock`, а `systemctl enable notenotes.service` безопасен: юнит
попадает в `encrypted-apps.target.wants`, который при загрузке не активируется.

## Ограничения и что дальше

Вне этой конфигурации:

- **Код приложения** — FastAPI-бэкенд и React-фронт. Заготовки сервисов
  закомментированы в `docker-compose.yml`, окружение для них — в `app.env`.
  Когда backend появится: раскомментировать сервисы и поставить
  `notenotes_backend_deployed: true`.
- **Client-side «сейф»** ТЗ §16.2 — работа в приложении, Фаза 4.
- **Записи в панели Hostens** — вне Ansible.
- **Prometheus/Grafana** — на 4 GB RAM не оправданы. Наблюдаемость: journald
  плюс `OnFailure` на юнитах бэкапа.
- **LUKS на root** — отклонён в пользу контейнера: отказ обратим (ОС грузится,
  SSH доступен), переустановка не нужна, разблокировка по SSH вместо VNC.

Место под данные: контейнер 40 ГБ из 80. Расширение без пересоздания:

```bash
sudo encrypted-lock
sudo fallocate -l 60G /var/lib/srv-crypt/data.img
sudo cryptsetup open /var/lib/srv-crypt/data.img srv_encrypted
sudo cryptsetup resize srv_encrypted
sudo e2fsck -f /dev/mapper/srv_encrypted
sudo resize2fs /dev/mapper/srv_encrypted
sudo encrypted-unlock
```

Не забыть обновить `luks_container_size_gb` в `main.yml`, иначе проверка
свободного места будет считать по старому значению.
