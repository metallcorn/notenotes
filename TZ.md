# ТЗ: Персональный ассистент («второй мозг») Notenotes

Версия: 1.1 · Дата: 05.08.2026

---

## 1. Суть продукта

Self-hosted система для аккумуляции личных и семейных данных с возможностью быстрого поиска по всему сразу: заметки, списки, документы, файлы, инвойсы, сохранённые сообщения из Telegram, новостные ленты.

Ключевая идея — вместо ручного поиска по облачным хранилищам, чатам и дискам всё лежит в одном месте и находится либо визуально (папки/теги), либо запросом на естественном языке.

**Масштаб:** 2–10 пользователей (владелец + семья + возможно друзья).

## 2. Технический стек

| Слой | Решение |

## 3. Модель данных

### 3.1 Основной принцип

Подход Notion: **одна универсальная таблица `items`** для любого контента (заметка, список, файл, инвойс) с типизированным «конвертом» и JSONB-полем `properties` для специфики конкретного типа.

Обоснование: схема на старте нестабильна, JSONB даёт нулевое трение при добавлении новых типов контента без миграций.

### 3.2 Структура `items`

Типизированные колонки (участвуют в фильтрах, правах, индексах):

- `id` (UUID)
- `space_id` — принадлежность спейсу
- `folder_id` — папка (строгое дерево)
- `author_id` — кто создал
- `material_type` — тип (note / list / file / invoice / dialog / …)
- `title`
- `content` — markdown-тело
- `created_at`, `updated_at`
- `is_public`, `share_token`, `share_password_hash`, `share_revoked`
- `embedding vector(N)` — для семантического поиска

JSONB `properties` — специфичные поля типа (для инвойса: контрагент, сумма, дата, статус; для файла: путь, mime-type, размер; для диалога: массив структурированных реплик с ролями; и т.д.).

**Индексы:** B-tree на типизированных колонках, GIN на `properties`, HNSW/IVFFlat на `embedding`, GIN на full-text search.

### 3.3 Прочие сущности

- `users` — пользователи
- `user_identities` — способы входа (provider + provider_user_id) для account linking
- `spaces` — личные и общие пространства
- `space_members` — участники спейса (+ статус приглашения)
- `folders` — строгое дерево папок
- `tags` — теги как полноценные сущности (свой id, можно переименовывать/сливать)
- `item_tags` — many-to-many, с привязкой к `user_id` (теги персональные)
- `notifications` — расширяемая система уведомлений с типом события
- `item_versions` — история изменений заметок
- `sources` — подключённые внешние источники (Telegram-каналы, RSS)

## 4. Аутентификация

Порядок реализации:

1. **Логин/пароль** — основной способ. Email-сервера нет, поэтому восстановление пароля **только вручную через админку** (или через привязанный Telegram). Риск потери доступа принят осознанно.
2. **Google OAuth** — добавляется следом как удобная альтернатива. Приложение остаётся в статусе Testing в Google Cloud Console, пользователи добавляются вручную в test users (верификация не нужна).
3. **Telegram Mini App** — добавляется позже, в первую очередь чтобы друзья могли попробовать без регистрации (авторизация через подписанный `initData`).

**Account linking:** таблица `user_identities` позволяет привязать несколько способов входа к одному аккаунту. Привязка второго способа происходит только из аутентифицированного контекста (настройки профиля).

**Админка:** ручной сброс пароля, управление пользователями.

## 5. Спейсы и права доступа

### 5.1 Модель

Всё содержимое живёт в спейсах. У каждого пользователя автоматически создаётся личный спейс; дополнительно можно создавать общие.

- **Создавать спейсы и приглашать может любой пользователь**
- **Все участники спейса равны** — читают и пишут всё, ролей owner/editor/viewer на MVP нет
- **Приглашение:** уникальная ссылка-инвайт + внутреннее уведомление приглашённому («вас добавили в спейс X», непрочитанное). Он может принять или отклонить; пригласившему приходит статус (принято / отклонено / ожидается)

### 5.2 Выход и удаление

- Участник вышел → просто теряет доступ. Контент остаётся в спейсе, остальные ничего не теряют
- **Удаление спейса** (аналог «удалить и выйти» в Telegram) — доступно любому участнику, немедленно отзывает доступ у всех. Сделано ради приватности, осознанно выбран более «жёсткий» вариант

### 5.3 История изменений

Все участники спейса видят полную историю: кто что менял и когда.

## 6. Навигация и структура

- **Папки — строгое дерево:** каждый item лежит ровно в одной папке
- **Теги — гибридный слой поверх:** item может иметь много тегов, что даёт «второе измерение» навигации
- **Единое дерево на все спейсы:** спейсы выступают корневыми папками верхнего уровня, внутри каждого своя вложенность

---

## 7. Заметки и редактор

- Формат хранения — **всегда Markdown**, независимо от режима редактирования
- **Переключатель между WYSIWYG и raw Markdown** — для обычных и продвинутых сценариев. WYSIWYG удобнее для вставки картинок
- **Картинки** хранятся отдельными файлами (диск/S3), в markdown только ссылка — не base64
- **Ссылки между заметками** — ручные, wiki-стиль `[[название]]` или прямая ссылка на item, бэкенд парсит и строит связи
- **Версионирование:** история изменений с возможностью отката к предыдущей версии

---

## 8. Теги и LLM-классификация

### 8.1 Теги

- Отдельная сущность со своим id (можно переименовать/слить везде сразу)
- **Глобальные на уровне пользователя** — один тег доступен во всех его спейсах
- **Персональные на общих item'ах** — на одном и том же общем item каждый участник тегирует по-своему

### 8.2 Авто-теги

- Запускаются **периодическим батчем** по неразобранным/непротегированным заметкам (раз в час/день), не блокируют UI и не выполняются на каждое сохранение
- **Визуально отличаются от пользовательских** (например, помечены звёздочкой), пользователь может удалить неверный тег
- **Логика подбора:** LLM в первую очередь проверяет и переиспользует существующие теги пользователя (чтобы не плодить «work» и «работа»), новый тег создаёт только если концепт не покрыт
- **Базовый словарь тегов общий для всех пользователей системы** (зашит в приложение) — снижает вариативность формулировок

---

## 9. Файлы и OCR

- **OCR запускается автоматически сразу при загрузке** — каждый файл идёт в очередь на распознавание/классификацию
- **Загруженный файл сразу становится обычным item'ом** в спейсе и виден в папке; теги и связи дописываются позже (без промежуточного «инбокса»)
- **PII-документы (паспорта и т.п.):** в индекс и в промпт LLM попадает **только тег/лейбл** («паспорт, владелец: X»), содержимое документа в LLM не уходит никогда. Файл отдаётся напрямую с диска по запросу
- Детект по MRZ-зоне и характерным признакам для авто-классификации документов

## 10. Поиск

- **Единый флоу:** быстрые результаты (ключевые слова / теги / full-text) появляются мгновенно, AI/векторные результаты подгружаются следом отдельным блоком «расширенный поиск» с видимым индикатором загрузки
- Это не два разных режима, а один поток с прогрессивной загрузкой
- **Область поиска:** ищет сразу по всем спейсам пользователя, с возможностью отфильтровать результаты по конкретному спейсу постфактум

## 10a. Диалоговые заметки (AI-ассистент)

### Суть

Голосовой/текстовый ввод работает не только как диктовка, но и как **разговор с ассистентом**: поговорили, уточнили, сохранили. Это основной сценарий «второго мозга» — ради него изначально задумывались MCP и RAG.

### Структура

- Отдельный `material_type` = **`dialog`**
- Реплики хранятся **структурированно в JSONB** (роль + текст + метаданные вызванных инструментов) — чтобы можно было точно адресовать конкретную реплику
- Осознанный trade-off: сложнее в редакторе, но даёт точную адресацию для суммаризации по фрагменту

### Суммаризация

- Можно обработать **выделенную секцию или весь диалог** — LLM сжимает разговор до сути, удобной для чтения и вспоминания
- **Пользователь каждый раз выбирает:** заменить исходный текст или добавить резюме рядом (оригинал остаётся)
- Механизм в редакторе: выделил фрагмент → применил действие
- Опирается на историю версий (раздел 7) — суммаризация деструктивна, откат обязателен

### Доступ к данным

- LLM в диалоге **видит базу пользователя** и может искать/ссылаться на неё — полноценный ассистент, а не изолированный чат
- **Область контекста:** все спейсы пользователя (та же логика, что у обычного поиска)
- Retrieval-слой **общий** с «расширенным поиском» из раздела 10 — не делать два разных механизма

### PII в контексте

- По умолчанию PII-документы отдают в контекст только тег/имя (см. раздел 9)
- Пользователь может **вручную разрешить доступ** к конкретному документу внутри диалога
- ⚠️ UI должен формулировать это честно: не «включить доступ», а **«отправить содержимое документа в LLM»** — решение должно приниматься осознанно

## 10b. Tool-calling слой и веб-поиск

### Архитектура

LLM работает через набор инструментов (function calling / MCP), оркестрация — на стороне бэкенда:

- `search_base(query)` — поиск по собственной базе (общий retrieval-слой)
- `web_search(query)` — внешний веб-поиск
- (расширяемо в будущем)

### Веб-поиск

- **Провайдер: Tavily** — 1000 кредитов/месяц бесплатно с обновлением, заточен под LLM (чистые сниппеты без HTML-мусора)
- **Реализуется через абстракцию** `web_search(query) -> results`, чтобы провайдера можно было заменить без переписывания остального кода
- **Включается тумблером в диалоге:** включил — модель ищет когда считает нужным, без запроса разрешения на каждый поиск

### Обязательный предохранитель

**Лимит поисков на один ход диалога** (ориентир: 5). Без него агентный цикл способен сжечь месячный бесплатный лимит за один неудачный запрос — самая частая проблема с tool-calling.

### Отвергнутые варианты

| Вариант | Почему нет |
|---|---|
| Mistral Agents API (встроенный веб-поиск) | $30 за 1000 вызовов, нет бесплатного лимита, привязка к их stateful Agents API. Подписка Le Chat **не покрывает** API — это раздельные продукты |
| Gemini grounding как tool для Mistral | Бесплатно в нужном объёме (5000/мес), но двойная латентность, двойные токены, и Gemini отдаёт готовое резюме вместо сырых результатов — Mistral работает с пересказом из вторых рук |
| Serper | Дешевле ($0.30–1/1k), но бесплатный лимит разовый (2500), сырые SERP, и висит риск от иска Google к SerpAPI |
| Свой SearXNG | Бесплатно и приватно, но ещё один сервис на VPS с 4 GB RAM + блокировки |

## 11. Публичный шаринг

- Работает **для любого типа item** (заметка, список, файл) — единый механизм
- Ссылка **«живая»** — всегда показывает актуальную версию на момент перехода, не снэпшот
- **Только чтение** для всех, у кого есть ссылка (без редактирования/комментирования на MVP)
- Токен — длинная случайная строка (не последовательный id), не индексируется поисковиками
- Опциональный **пароль на страницу** и **отзыв доступа**

## 12. Списки и совместное редактирование

- **Реалтайм-синхронизация:** optimistic UI + WebSocket, отметка пункта видна другим участникам мгновенно
- **Разрешение конфликтов:** last-write-wins на уровне отдельного пункта (не всего списка целиком)

## 13. Уведомления

Расширяемая система с самого начала: единая таблица `notifications` с типом события (инвайт, изменения в списке и т.д.), центр уведомлений в интерфейсе с непрочитанными.

Комментарии/обсуждения на item'ах — **не нужны**, достаточно контента и истории изменений.

## 14. Голосовые заметки

- **Общий механизм независимо от канала** (Telegram-бот, веб-UI, будущие каналы)
- Аудио транскрибируется при поступлении (Deepgram / Palabra)
- **По умолчанию сохраняется только текст**, аудио удаляется
- Пользователь может явно сохранить аудио как голосовую заметку, если нужно

## 15. Внешние источники

### 15.1 Telegram Saved Messages

- Требует **MTProto user-auth** (Telethon), не Bot API
- **Изоляция:** отдельный Docker-контейнер только под MTProto-сессию, общается с основным бэкендом через узкий внутренний API. Сессия физически недоступна из основного приложения
- **Синхронизация:** непрерывный real-time listener через event handlers
- Session-файл — в volume с ограниченными правами, вне образа, вне незашифрованных бэкапов

⚠️ **Риск:** session-файл = полный доступ к личному Telegram-аккаунту (все чаты, отправка от твоего имени). Это самая чувствительная точка системы.

### 15.2 Telegram-каналы

- Список для индексации **выбирается из каналов, на которые пользователь уже подписан** в своём аккаунте — система предлагает список
- Только curated-подход, никакой попытки классифицировать весь Telegram

### 15.3 RSS/Atom

Периодические фетчеры по добавленным лентам.

## 16. Шифрование и безопасность

### 16.1 Основное хранилище

- Шифрование диска (LUKS) + TLS + шифрованные бэкапы
- Бэкенд работает с расшифрованными данными в памяти — это **необходимо** для LLM/OCR/векторного поиска
- **Не zero-knowledge**, риск компрометации рантайма принят осознанно
- Основная защита — операционная гигиена: SSH только по ключу, файрвол, минимальная поверхность атаки, регулярные патчи

### 16.2 Зашифрованный «сейф»

Отдельная параллельная подсистема для чувствительного (паспорта, финансовые документы):

- Client-side шифрование по паролю, заданному пользователем
- Используется проверенная библиотека (age / libsodium), не самописная крипто-логика
- **Максимальная переносимость:** шифрование завязано только на пароль, не на устройство — тот же пароль работает где угодно
- На конкретном устройстве после первого ввода можно включить биометрию/PIN как локальный shortcut

**Принятые ограничения сейфа:**
- Содержимое **не индексируется**, не участвует в поиске, не обрабатывается LLM
- Забыл пароль → данные потеряны безвозвратно (нужен явный warning; recovery-фраза — опция на будущее)
- Метаданные (имя файла, размер, дата) серверу видны, если не шифровать отдельно
- Нет связей между сейфом и обычным хранилищем — два независимых мира

Реализуется **после** того как основная система обкатана, не в первой итерации.

## 17. Бэкапы и экспорт

- **Бэкапы выносятся на внешнее хранилище** (MEGA / S3) — защита от отказа всего сервера
- **Ручной экспорт** — пользователь может выгрузить всё сам (markdown + json архив)
- Обязательно: бэкап перед каждой миграцией БД

---

## 18. Offline

Базовый **offline read-only через PWA-кэширование** — ранее открытый контент доступен без интернета. Полноценное offline-редактирование не требуется.

## 19. Фазы разработки

### Фаза 1 — Ядро
Спейсы, папки, заметки (MD-редактор с переключателем), списки, теги, full-text поиск, аутентификация (логин/пароль), уведомления, история версий, публичный шаринг, WebSocket для списков.

### Фаза 2 — Каналы, медиа и AI-слой
Telegram-бот, голосовые заметки, загрузка файлов, OCR-пайплайн, векторный поиск, авто-теги через LLM, диалоговые заметки с tool-calling (поиск по базе + веб-поиск), суммаризация.

### Фаза 3 — Внешние источники
MTProto-спайк (Saved Messages), Telegram-каналы, RSS/Atom.

### Фаза 4 — Расширения
Google OAuth, Telegram Mini App, зашифрованный сейф, файловый конвейер с MEGA.

## 21. Известные риски

1. **Качество retrieval** — «засосать данные в одну систему» ≠ хороший поиск. Требует итераций на реальных данных, особенно при разнородном контенте (текст + сканы + таблицы)
2. **Точность OCR** — часть документов распознается криво, нужен механизм проверки/исправления
3. **Стоимость LLM API** при ежедневном использовании, особенно vision-запросы
4. **MTProto-сессия** — самая чувствительная точка, изоляция обязательна
5. **Доверие к авто-классификации** — если LLM «потеряет» что-то важное один раз, доверие не вернуть. Отсюда требование: предлагать, а не молча перекладывать
6. **Миграции БД** — риск снимается процессом (бэкап перед миграцией, тест на копии), а не выбором технологии
7. **Агентный цикл в tool-calling** — модель способна нагенерить каскад вызовов и сжечь бесплатные лимиты за один запрос. Лимит на ход обязателен с первой версии
8. **Ручное разрешение PII в диалоге** — самая опасная точка с точки зрения приватности: один неосознанный клик отправляет паспорт во внешний LLM. Требует честной формулировки в UI, а не generic «разрешить доступ»
9. **Деструктивность суммаризации** — «сжали разговор до сути» необратимо без версий. История версий из необязательной фичи становится обязательной
